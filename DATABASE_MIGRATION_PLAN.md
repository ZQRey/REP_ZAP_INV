# План миграции схемы и данных

REP_ZAP_INV · 28.09.2026 · commit `ecd7afa17ec1166b1427ca53b041a8e4e360137f`.

Схема ниже восстановлена по исходному коду. Фактическая production-схема и данные не получены. SQL/скрипты к рабочим БД не выполнялись. Это план, а не готовая к запуску миграция.

## Текущее состояние

Два независимых `Base`/engine/session registry ([SHARED/database.py:27](https://github.com/ZQRey/REP_ZAP_INV/blob/ecd7afa17ec1166b1427ca53b041a8e4e360137f/SHARED/database.py#L27), [CARTRIDGE/app/database.py:13](https://github.com/ZQRey/REP_ZAP_INV/blob/ecd7afa17ec1166b1427ca53b041a8e4e360137f/CARTRIDGE/app/database.py#L13)) направлены по умолчанию в один SQLite `BD/app_unified.db`, а root compose направляет оба через env в PostgreSQL. Standalone Cartridge compose задаёт другой SQLite `/data/cartridges.db`. SHARED содержит 22 таблицы; legacy Cartridge повторно описывает 9 из них. Модели не являются точной копией: Branch.network_subnets и связи расширены, AppUser.default role расходится. Две metadata не означают две изолированные БД.

| Группа | Таблицы | Ключевые зависимости |
|---|---|---|
| Identity/config | branches, app_users, ad_users, system_settings, audit_logs | app_users.branch_id → branches; audit_logs.user_id → app_users; employee key — текстовый samaccountname. |
| Cartridge | cartridge_models, cartridges, batches, batch_items, history_logs | cartridges.branch/current_user; batch_items → batches+cartridges; history → cartridge. Cartridge.model — строка, не FK справочника. |
| Assets/Repair | equipment_models, assets, repair_batches, repair_batch_items, repair_parts_used, spare_parts_warehouse, equipment_history_logs | assets → branch/AD user/floor/zone; repair item → batch+asset; parts → item; warehouse → branch. |
| Location/network | floors, zones, cable_paths, network_switches, switch_ports | floor→branch; zone/cable→floor; switch→asset (unique); port→switch/zone/connected_asset. |

Значимые циклы загрузки: floors/zones создаются до записи spatial FK assets; network_switches после assets; switch_ports после обоих. ORM relationships не заменяют DB constraints и не гарантируют согласованность branch/floor/zone. Evolution schema управляется внешним продуктом и не должна включаться в autogenerate бизнес-миграций.

## Дефекты существующего переноса и reset

[BD/migrate_data.py:21–197](https://github.com/ZQRey/REP_ZAP_INV/blob/ecd7afa17ec1166b1427ca53b041a8e4e360137f/BD/migrate_data.py#L21) нельзя использовать как production migration без переработки:

1. `init_db()` сначала создаёт default branch/admin, затем импортирует старые записи с исходными ID. Проверяет существование branch по name, пользователя по username, cartridge по marker, batch по act_number, но не строит old→new ID mapping. Совпадение имени при другом ID и коллизия PK нарушают ссылки.
2. История `history_logs` и настройки `system_settings` вообще не переносятся. Исходные created_at/updated_at не сохраняются; cartridge.condition принудительно `working`. Это потеря смысловых данных.
3. Каждый блок commit отдельно, catch+rollback только текущего блока, в конце безусловный текст об успешном завершении. Возможен неполный импорт с успешным сообщением.
4. `db.merge(BatchItem)` ориентирован на PK без migration ledger и mapping; повторный запуск способен заменить не ту связь при конфликте ID.
5. Existing AppUser password_hash перезаписывается без подтверждения identity/provider. Нет сохранённого отчёта конфликта или policy приоритета.
6. Явные ID не сопровождаются reset PostgreSQL sequences; следующая обычная insert может конфликтовать. Нет сверки totals/foreign keys, режима dry-run, backup или stop-on-error.
7. Источник жёстко SQLite-path; назначение реально определяется env SessionLocal, несмотря на сообщения про `BD/app_unified.db`. Перед запуском оператор может ошибиться в целевой БД.
8. Нет проверки значений enum/case, timezone и FK enforcement. Старые строки статуса надо сверить с реальным SQLEnum storage, а не предполагать lower-case values.

[CARTRIDGE/reset_data.py:27–36](https://github.com/ZQRey/REP_ZAP_INV/blob/ecd7afa17ec1166b1427ca53b041a8e4e360137f/CARTRIDGE/reset_data.py#L27) удаляет **все** cartridges/batches/items/history без фильтра «тестовые». `--clear-ad-users` затрагивает общий справочник; `--full` удаляет DEFAULT_SQLITE_PATH, независимо от активного env DATABASE_URL, после чего init_db работает с engine из env. В unified deployment последствия могут не соответствовать описанию команды. Не применять эти scripts к production. В текущем аудите они не запускались.

## Пошаговая процедура migration

### DB0 — Сбор фактического baseline

DBA собирает read-only schema dump каждого deployment: версия PG/SQLite, tables/columns/types/defaults/constraints/indexes/sequences, enum labels, timezone, row counts, размеры, migration history (если внешний процесс есть). Проверить включение SQLite foreign_keys на реальных соединениях: в коде PRAGMA не найден. Сохранить exact application image/config без секретов. Закрепить backup ID, контрольную сумму и успешный restore в изолированную среду.

Профилировать: NULL/dangling branch, несовместимые floor/zone, duplicate lower(username), domain collisions, duplicate markers/serials/AD GUID/ports, mixed-branch batches, enum values, invalid JSON/координаты, negative costs/quantities и потерянные references. Численные результаты сейчас неизвестны: запросы должны быть выполнены на копии, а не выдуманы из исходников.

### DB1 — Canonical metadata и Alembic baseline

Объединить модели в один registry в M4, ещё без destructive DDL. Сравнить generated schema с каждым baseline. Создать проверяемый baseline revision для fresh install и отдельные upgrades для реально существующих вариантов. `stamp` применять только после проверки equivalence; запрещено просто пометить старую БД новой revision. Exclude Evolution schema. Одна migrator role с DDL, runtime роль только DML; один migration job с advisory lock. Startup проверяет совместимую revision и readiness, не исправляет схему.

### DB2 — Additive expansion

Добавить новые таблицы/nullable fields: external identities (provider+external immutable ID), branch memberships/permissions, asset provenance, typed credential references, outbox/delivery ledger, network observations, actor IDs, version, model IDs. Секреты сначала копировать в защищённое хранилище с mapping; plaintext удалять только после сверки. Добавлять индексы подходящим для PostgreSQL способом с контролем lock/statement_timeout, не в одной огромной транзакции с backfill.

### DB3 — Детерминированный ETL и mapping

Использовать staging schema и таблицу `migration_run/source/entity/old_id/new_id/status/checksum`. Источник открывать read-only. Порядок:

1. Branch и SystemSetting (mapping старых/новых ключей, secrets отдельно).
2. AD employee identity, AppUser/external identity/membership; коллизии вручную, без auto-merge по display_name/username.
3. CartridgeModel и EquipmentModel; string→model_id только при однозначном соответствии.
4. Floors, Zones, CablePaths.
5. Cartridges и Assets (сохранить все timestamps, statuses, conditions, notes/specs, IDs или mapping).
6. Cartridge/Repair batches и их items, parts, warehouse.
7. NetworkSwitch/ports, размещение и нормализованные network identifiers.
8. Полная история и audit, затем сохранённое integration state по отдельному provider runbook.

Каждый chunk транзакционен и checkpointed; ошибки — fail/карантин с деталями, не «успех». Повтор запуска с тем же input ничего не меняет. Existing user hashes сохраняются только для доказанно той же identity; не сбрасывать password/role. PostgreSQL sequence значения синхронизировать после explicit IDs до разрешения insert, с проверкой `max(id)` и первого нового insert.

### DB4 — Reconciliation и constraints

Проверить counts по таблице/филиалу/статусу/периоду, old→new mapping completeness, все FK/unique, выборочные row hashes, номера актов, timestamps, историю и суммы Decimal. Для каждой intentional разницы (quarantine/demo/duplicates) — подписанный exception register; требование не всегда буквальное count equality после согласованной дедупликации.

Только после cleanup включать NOT NULL/CHECK/FK/unique. Для портов unique(switch_id,port_number); для batch-item pairs определить допустимость повторного ремонтного цикла; для membership — запрет неявного global. Composite FK/denormalized tenant columns либо строгие application checks должны покрывать cross-tenant связи; RLS как дополнительный слой — после теста tenant context с connection pool, separate migrator/admin bypass и fail-closed reset context. Не вводить RLS поверх общей superuser-role, считая это защитой.

### DB5 — Переключение SQLite→PostgreSQL / canonical schema

Если production уже PG, ETL SQLite не нужен — применяется schema upgrade к копии и затем controlled rollout. Если SQLite: краткое окно остановки writers предпочтительнее непроверенного dual-write. Остановить API mutations/AD/network/WA workers, зафиксировать финальный snapshot/high-water mark, выполнить финальный delta и reconciliation. Переключить DSN/credentials единственного writer, проверить read/write/sequence/enum/JSON и reports, затем включать фоновые задания по одному. Redis cache очищать только namespaced/versioned, не весь shared instance.

### DB6 — Окно наблюдения и contract

Сохранять источник read-only и mapping до истечения согласованного окна. Следить за 409/errors, orphan metrics, reconciliation totals, queue lag и sequence failures. После подтверждения отсутствия legacy consumers удалять старые поля, aliases, plaintext и технические staging records по retention policy отдельной migration. Это destructive этап.

## Rollback

- До переключения target можно пересоздать из чистой копии; исходник не изменяется.
- После переключения без новых записей возможен возврат на read-only проверенный источник.
- После новых записей старый snapshot не является полноценным rollback: нужен останов writers, reverse replay по ledger либо forward fix. Нельзя одновременно открыть две БД на запись.
- Обратное преобразование enums/timezones/identity merge может быть неоднозначным; сохранять source columns/snapshots до contract.
- Backup включает PostgreSQL, maps/uploads, credential-reference mapping и Evolution sessions. Redis не считать единственным durable delivery ledger. Restore должен быть реально проверен.

## Обязательные проверки перед запуском

Fresh install и upgrade каждой обнаруженной исторической схемы; migration run twice; failure halfway/resume; concurrent migration lock; old/new binary compatibility; restrictive runtime DB role; PostgreSQL enum/JSON/text queries; TZ boundary reports; branch A/B/NULL; duplicate counters and ports; сохранение history/cost totals; недоступные integration adapters; restore и new writes после restore.

Отдельно: не запускать `reset_data.py`, текущий `migrate_data.py` или старые destructive tests как способ «подготовить» production. SQLAlchemy create_all и ручные ALTER не являются replacement migration history.

Тип JSON отличается от текста; выражение ilike требует явной корректной операции/extraction в PostgreSQL. Для проектирования преобразований использована [официальная документация JSON PostgreSQL](https://www.postgresql.org/docs/current/datatype-json.html); конкретный compatibility defect надо воспроизвести на принятой версии PG 15 в integration test.


## Дополнительный destructive sync

[REPAIR/app/services/model_parser_service.py:442–522](https://github.com/ZQRey/REP_ZAP_INV/blob/ecd7afa17ec1166b1427ca53b041a8e4e360137f/REPAIR/app/services/model_parser_service.py#L442) удаляет модели по шаблону имени с отдельным commit, затем глобально переименовывает/переклассифицирует workstation/laptop/server assets и перезаписывает model notes/specs. Вызывается `/models/sync-from-ad` и после AD computer sync. Это не только обновление справочника: перед миграцией требуется snapshot исходных имён и ручных спецификаций, source-aware merge и одна проверяемая операция. Ошибка после первого commit уже не вернёт удалённые модели.
