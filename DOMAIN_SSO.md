# Автоматический доменный вход

Настройка находится в главном портале: «Настройки» → блок LDAP → «Автоматический вход под доменной учётной записью». Доступна только суперадминистратору.

1. Настройте LDAP, проверьте подключение и синхронизируйте сотрудников.
2. Создайте DNS-имя сайта и настройте HTTPS с доверенным сертификатом. Открывайте сайт по этому имени, а не по IP.
3. В AD зарегистрируйте единственный SPN `HTTP/<DNS-имя сайта>` на отдельной сервисной учётной записи. Администратор домена должен сформировать для неё keytab с этим principal и realm. Делегирование учётных данных не требуется.
4. В веб-панели укажите DNS-имя сайта, Kerberos realm (например, `EXAMPLE.LOCAL`), загрузите keytab и включите автоматический вход. Сохраните настройки.
5. Для доменных компьютеров разрешите интегрированную авторизацию этого сайта в политике браузера. В Edge используется `AuthServerAllowlist` с конкретным именем сайта. Не разрешайте все сайты.

Приложение проверяет Kerberos-билет средствами GSSAPI. Из заголовков `X-Remote-User` и подобных имя пользователя не принимается. Права и филиал определяются базой приложения. Новый доменный пользователь получает роль «Пользователь», филиал определяется существующей привязкой владельца картриджей. Совпадение с локальной учётной записью, отключённая запись или чужой realm блокируют вход.

Локальная авторизация и ручной вход через LDAP сохраняются. При выключенном или незавершённом SSO, неподходящем адресе сайта либо неудачной проверке билета показывается обычная форма входа. После явного выхода SSO не повторяется в этой вкладке до её закрытия.

Сайт не может напрямую определить, под какой Windows-учётной записью запущен браузер. Доменный вход зависит от наличия билета и политики браузера. Если браузер не может передать билет автоматически, он может показать собственный запрос учётных данных; его можно отменить и использовать форму приложения.

Keytab хранится в `BD/sso/http.keytab`, недоступен через HTTP и исключён из Git. Он сохраняется в существующем Docker-томе BD. При переносе проекта перенесите этот файл вместе с данными приложения и сохраните ограниченные права доступа; новый keytab загружается через панель. Системные и Python-зависимости устанавливаются при `docker compose up --build`; дополнительные настройки внутри контейнера не нужны.

Если keytab должен меняться, сначала выключите SSO, загрузите новый файл и включите его снова. Доступ к AD, DNS, сертификату и политике браузера настраивается вне приложения: LDAP-пароль сам по себе не позволяет проверять Kerberos-билеты.

Развёртывание кода не включает SSO автоматически. Полная проверка требует доменного рабочего места после настройки LDAP, DNS, HTTPS, SPN и keytab. На текущем адресе `http://172.16.16.60/` остаётся ручной вход.

Источники: [GSSAPI: проверка контекста и keytab](https://pythongssapi.github.io/python-gssapi/stable/gssapi.html), [Microsoft Edge: AuthServerAllowlist](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-policies/authserverallowlist).
