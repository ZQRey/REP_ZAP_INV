# Security hardening — 28.09.2026

База изменений: `main@ecd7afa17ec1166b1427ca53b041a8e4e360137f`. Исходный аудит находится в [PR #1](https://github.com/ZQRey/REP_ZAP_INV/pull/1). Этот документ описывает изменения кода и условия развёртывания, а не подтверждение безопасности действующего production.

## Реализовано

- Общая конфигурация `SHARED/security_config.py`: обязательный случайный JWT secret, env или `*_FILE`, production по умолчанию; PostgreSQL и Redis с credentials обязательны; при включении интеграций обязательны соответствующие secrets. Никаких секретных значений по умолчанию. Секреты интеграций в production берутся из окружения/файлов, прежние значения БД не используются.
- Удалены автоматические admin provisioning, повышение роли при startup и изменение AD usernames при startup. Администратор создаётся явно через `python -m SHARED.bootstrap_admin --username <имя>`, пароль запрашивается скрыто. Существующие пользователи не удалены и их пароли автоматически не заменены.
- Один JWT verifier для обоих auth services: HS256, issuer, audience, обязательные exp/iat/nbf/sub/jti, aware UTC; 30 минут по умолчанию, максимум 120. Старые токены без этих claims отвергаются. Новый PBKDF2 SHA256 hash использует 600000 итераций, прежние 100000-итерационные hashes читаются для совместимости. Новые пароли 12–1024 символа; bootstrap минимум 16.
- Root, legacy и mounted login используют один limiter: 10 попыток на account и 50 на IP за 300 секунд, атомарный Redis Lua, 429/Retry-After; при недоступности Redis — 503, а не обход защиты. Только test/development без Redis используют ограниченную thread-safe память. Считаются и успешные попытки. Имена в Redis keys хешированы, паролей там нет.
- Generic login failures; заблокированный пользователь и несовпадение local/AD provider не допускаются. AD не создаёт учётки автоматически: администратор заранее назначает `auth_type=ad`, sAMAccountName, роль и филиал. LDAP filter escaping, проверка доменного суффикса, поиск через bind account и проверка пароля найденного DN; обходная цепочка bind-кандидатов удалена.
- JWT никогда не передаётся через URL. API отвергает query `token`. Frontend использует sessionStorage одного origin; старое localStorage очищается. Переходы между модулями без токена в адресе. Печать получает документ через authenticated fetch. Logout удаляет token текущей вкладки; это не серверный отзыв украденного bearer token.
- Общий обязательный auth guard для business API и печати, включая mounted apps. Печать дополнительно проверяет branch ownership. Read DTO оборудования/коммутаторов не содержит username/password/SNMP community/API keys или произвольный extra_params. Есть `credentials_configured`; секреты вводятся только на запись, пустое поле сохраняет прежнее значение. Настройки маскируются для всех ролей, в том числе superadmin, в GET и POST/PUT.
- HTTPS для Omada с CA verification, SSH RejectPolicy с известными host keys, LDAP LDAPS либо StartTLS **до bind** с проверкой сертификата и hostname. Управление устройствами в production ограничено literal IP из `NETWORK_ALLOWED_CIDRS`; loopback/link-local/multicast запрещены. DNS для switch IP не разрешается, что исключает rebinding этого пути.
- Demo выключено по умолчанию и запрещено в production независимо от сохранённого `allow_demo_fallback`. Нет demo AD/этажей/сетевых событий/справочников в production. Незавершённый SNMP bridge walk возвращает ошибку вместо фиктивной пустой успешной таблицы. Repair connection test использует настоящий transport test и не выдумывает MAC count.
- Удалены отслеживаемые deployment TLS key/certificate. Добавлены ignore/build exclusions, пустой `.env.example`, security regression scanner и CI. Полная история **не очищена** — см. [SECURITY_HISTORY_CLEANUP.md](SECURITY_HISTORY_CLEANUP.md).
- PostgreSQL, Redis, Evolution и backend не публикуют host ports в production Compose; снаружи только nginx 80/443. HTTP перенаправляется на HTTPS. Непривилегированный пользователь приложения, без bind mounts исходников. Redis требует пароль. Access logs не содержат query/referrer/headers; Uvicorn access log отключён, nginx error log ограничен critical. Ошибки интеграций не возвращают upstream body; SQL parameters скрыты; logging redactor удаляет известные secrets, bearer и типовые credential fields.
- Все CORS origins задаются через `CORS_ORIGINS`, wildcard запрещён; production допускает только HTTPS origins. Validation errors не возвращают входные пароли. API responses `Cache-Control: no-store`.

## Перед развёртыванием

1. Ограничить доступ и выполнить ротацию из отдельного runbook. Резервная копия БД и проверка восстановления обязательны перед обновлением legacy startup schema. Этот PR не заменяет её на Alembic.
2. Создать независимые случайные secrets в secret manager. Заполнить `.env` вне Git либо передать env/secret files. Значения URI должны содержать URL-encoded passwords. Не сохранять результат `docker compose config` с раскрытыми значениями в логи/репозиторий.
3. Указать `DATABASE_URL`, `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `REDIS_URL`, `EVOLUTION_API_KEY`, `EVOLUTION_DATABASE_URL`, `EVOLUTION_REDIS_URL`. Redis URL `/0` используется приложением, `/1` — Evolution. Обе строки используют тот же **новый** Redis password. PostgreSQL password env не меняет пароль существующей роли автоматически: сначала сменить его в БД согласованно с клиентами. Предпочтительны отдельные ограниченные роли/БД приложения и Evolution.
4. При AD установить `LDAP_ENABLED=true`, `LDAP_BIND_PASSWORD`, настроить host/base DN/bind user через защищённую админку. `WHATSAPP_ENABLED=true` уже задан Compose. Отсутствующие обязательные secrets останавливают запуск. В development также обязателен новый `SECRET_KEY`; SQLite допускается только вне production.
5. Разместить **новую** TLS-пару в игнорируемом `nginx/ssl`, проверить срок/SAN/chain. Для частного CA смонтировать файл и задать `TLS_CA_FILE` в контейнере. Для SSH создать `secrets/ssh/known_hosts`; fingerprint подтвердить по независимому каналу. Один `ssh-keyscan` без сверки не устанавливает доверие. Для нестандартного порта запись `[host]:port`.
6. Задать явные HTTPS `CORS_ORIGINS`, например адрес фактического портала без завершающего `/`; пустой список допускает обычную работу same-origin. `NETWORK_ALLOWED_CIDRS` содержит только подсети управления устройствами. Портал должен обслуживаться одним origin для всех модулей.
7. Compose резервирует `172.30.88.0/24`, nginx `172.30.88.10`. Если подсеть пересекается с инфраструктурой, изменить и Compose, и Uvicorn `--forwarded-allow-ips` согласованно. Только этот nginx доверен как proxy; он перезаписывает X-Forwarded-For. Не ставить `*`. При запуске через другой proxy задать его точный доверенный адрес, иначе IP limit будет общим для proxy.
8. Подготовить bind-mounted `BD` и `uploads` с правами UID/GID 10001. Если имеются старые планы, перенести их из `LOCATION/app/static/uploads` в новый внешний `uploads` после резервного копирования. Удаление source mounts требует пересборки образа после изменений.
9. Сменить пароли старых default-аккаунтов, отключить неизвестные учётки, проверить роли/филиалы AD. При отсутствии администратора выполнить bootstrap внутри настроенного контейнера. Старые JWT перестанут работать; потребуется повторный вход. Не возвращать скомпрометированный JWT secret ради совместимости.
10. На staging проверить настоящий PostgreSQL/Redis, CA/hostname rejection, SSH known_hosts, AD login/sync, WhatsApp QR/send/reset, list/update оборудования с пустыми credential fields и печать обоих модулей. Legacy `CARTRIDGE/docker-compose.yml` теперь требует внешние PostgreSQL/Redis и защищённый ingress; самостоятельная публикация портов удалена. Для обычного развёртывания использовать корневой Compose.

## Проверки и ограничения

Локальные security tests используют отдельную временную SQLite БД, случайные credentials и mocks транспортов; не обращаются к реальным AD/WhatsApp/устройствам. Запуск: `python -m pytest`; scanner: `python scripts/check_security.py`. Синтаксис четырёх frontend JS проверяется Node. CI повторяет проверки на Python 3.11. Старые manual verification scripts требуют `APP_ENV=test` и `TEST_USER_PASSWORD`; это не гарантирует изоляцию, поэтому использовать их можно только с отдельно заданной тестовой DATABASE_URL.

Docker daemon в рабочем окружении недоступен: сборка образов и nginx runtime не подтверждены. Compose разобран YAML-проверками; настоящие PostgreSQL/Redis и интеграции требуют staging. Dependencies остаются диапазонами, CVE/lock/SBOM не закрыты этим изменением. Custom scanner — регрессионная эвристика, а не доказательство отсутствия всех секретов.

### Остаточные риски аудита

Это hardening перечисленных механизмов, **не закрытие всего SECURITY_AUDIT**. S06–S09: полная branch/object isolation в Cartridge, Repair и Location, массовые операции, межфилиальные связи и auto-heal в GET ещё требуют отдельной миграции и матрицы тестов. Новая обязательная authentication сама по себе не устраняет IDOR. Do not expose to mutually untrusted branches until these are fixed.

Также остаются: шифрование уже сохранённых сетевых credentials в БД и их резервных копиях; безопасная обработка SVG/uploads и XSS/CSP/CDN supply chain; полный server-side session revocation; идемпотентность WhatsApp; Alembic вместо startup DDL; секреты в старых внешних логах/клонах/образах. SessionStorage доступен JavaScript и не защищает от XSS. SNMP v2c передаёт community по сети без шифрования: нужен изолированный management network и отдельная миграция SNMPv3. Само сохранённое значение credentials не удаляется автоматически, чтобы не обрывать интеграции без подготовленной ротации.

## Откат и потенциально destructive действия

В этом изменении нет DROP/TRUNCATE, автоматической очистки данных или rewrite Git history. Удалены только закоммиченные TLS deployment files; без новой пары nginx не стартует. Старые токены инвалидируются, default admin больше не создаётся, неподтверждённые TLS/SSH подключения прекращаются, unprovisioned AD users не входят, demo и прямые контейнерные порты недоступны — это намеренные изменения безопасности. Повышенный формат password hash требует этого verifier: старый backend не прочтёт новые hashes. При откате сохранять новые secrets и verifier, не откатывать credentials на скомпрометированные. Rewrite истории и ручная очистка credentials/логов выполняются отдельно после согласования.
