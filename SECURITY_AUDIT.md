## Данные и конкурентность, влияющие на безопасность

- Startup ALTER/create_all без migration lock; несколько процессов могут одновременно изменять схему/seed. Broad catch скрывает несовместимость. На PostgreSQL после SQL error транзакцию нельзя продолжить без rollback/savepoint.
- `count()+1` в Cartridge batches и fallback Repair act number; основной Repair алгоритм last+1 тоже имеет race. Уникальность номера превращает гонку в ошибку, но не предотвращает её.
- Нет уникальности `(switch_id, port_number)` и блокировки concurrent poll; повторные запросы меняют связи и историю. Bulk workflows не требуют допустимого предыдущего статуса или полного совпадения requested/found IDs.
- Экспорт/списки/пакеты часто не ограничены, query limit иногда имеет только верхнюю границу; большие запросы, upload и интеграционные timeout занимают ресурсы. Это risk exhaustion, а не доказанный production DoS.
- Деструктивные scripts и миграция данных подробнее разобраны в DATABASE_MIGRATION_PLAN.md.

## Что уже сделано правильно в исходном коде

JWT проверяет разрешённый HS256; authenticated dependencies перечитывают active user/role из БД. Пароли хэшируются с индивидуальной случайной солью PBKDF2 и сравниваются constant-time. App-users management и LDAP settings/sync ограничены superadmin. QR/reset чужого WA instance запрещён non-superadmin. Создание Cartridge batch принудительно использует филиал оператора и проверяет принадлежность найденных картриджей. ORM и показанные raw DELETE/UPDATE используют параметры; SQL injection для этих операций не подтверждён. Эти меры надо сохранить и покрыть regression-тестами.

## Проверки без обращения к production

В будущей isolated test DB: anonymous и invalid-token GET каждого business endpoint → 401; пользователь филиала A обращается к объекту B → deny без изменения БД; NULL/unknown-role → deny; bulk A+B → атомарный отказ; все response DTO → отсутствие credential fields; root и mounted aliases → одинаковая policy. Для AD — mocked TLS/identity/filter tests; никаких запросов с тестовыми payload к реальному каталогу. Для WA — fake gateway с потерянным ответом/403/concurrent QR; доказать отсутствие непредусмотренного reset/send. Для сети — контролируемый адаптер, запрещённый target блокируется до соединения.

## Границы CI/CD проверки

В дереве нет `.github/workflows`, CI-конфига, Alembic, lock-файла, pytest configuration. API GitHub вернул `workflow_runs.total_count=0`, для `main` — `protected=false` и пустые required checks. Запрос rulesets вернул 403 с ограничением тарифа; отдельный endpoint workflows недоступен через используемый connector. Поэтому внешние CI-системы и org-level controls не исключены. Это не отказ auto-review, а ограничения чтения GitHub API.

Версионные CVE требуют будущего lock/SBOM + dependency/container scan; список нижних границ `>=` не показывает реально установленную версию и не позволяет честно объявить пакет уязвимым либо безопасным.

По TLS LDAP вывод дополнительно сверён с [официальной документацией ldap3](https://ldap3.readthedocs.io/en/latest/ssltls.html): без явно заданного валидирующего Tls сертификат не проверяется. Остальные выводы основаны на ссылках на код данного commit.
